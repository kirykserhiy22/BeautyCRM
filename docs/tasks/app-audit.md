# Задача: повний технічний аудит Beauty Base

Прочитай `CLAUDE.md`. Аудит робимо на свіжому `main`, ПІСЛЯ злиття `feature/profession-system`.
Гілка: `chore/app-audit`.

## Головне правило
Це аудит, а не ремонт. Код додатку НЕ змінюй. Дозволено тільки:
- створювати файли в `docs/audit/`;
- додавати тести в `BeautyCRMTests` / `BeautyCRMUITests`, щоб перевірити поведінку.
Кожну знайдену проблему записуй у звіт. Виправлення підуть окремими задачами.

## Результат
1. `docs/audit/REPORT.md`: звіт українською, простими словами (Сергій читає код, але не пише).
2. `docs/audit/screenshots/<тема>/<NN-екран>.png`: скріншоти всіх екранів у кожній темі.
3. `docs/audit/features.md`: повний перелік функцій для користувача (див. розділ 6).
4. `docs/audit/ui-inventory.md`: інвентар UI-елементів для майбутньої дизайн-системи (див. розділ 7).

## 1. Збірка і тести
- Чиста збірка (`xcodebuild clean build`). Виписати ВСІ warnings із файлом і рядком.
- Запустити всі тести. Записати, що пройшло й що впало.

## 2. Карта архітектури
- Шари: View → менеджери стану (`EnvironmentObject`) → рушії/сервіси → SwiftData → файли/UserDefaults.
- Навігація: `AppRouter` (усі екрани та переходи між ними), вкладки, sheets, `NavigationLink`.
- Що де зберігається: SwiftData, файли фото, UserDefaults (кожен ключ).
- Діаграми у форматі Mermaid прямо в `REPORT.md`: архітектура, навігація, зв'язки моделей (`erDiagram`).

## 3. Моделі й цілісність даних
Для кожної моделі: поля, зв'язки, хто створює, хто змінює, хто видаляє. Окремо перевір:
- що відбувається з `Appointment`, коли видаляють клієнта (`clientID` / `clientName`);
- що відбувається з послугою в записі, коли видаляють послугу з прайсу;
- чи всюди однаково працює м'яке видалення (`deletedAt`) і чи кожен `@Query`/`FetchDescriptor`
  фільтрує видалене та чужі дані (`userID` / `workspaceID`);
- чи всі гроші — `Decimal`, а не `Double`;
- `ClientPhoto`: чи видаляються файли з диска разом із записом; чи не лишаються «сироти».

## 4. Бізнес-правила: перевірити ТЕСТАМИ
Для кожного правила напиши тест (або знайди існуючий) і запиши результат:
- накладки часу: межі (кінець одного = початок іншого), записи через північ, скасовані/завершені
  не блокують; пропозиція найближчого вільного слоту;
- дублікати клієнтів: регістр, пробіли на початку/в кінці, однакові імена з різними телефонами;
- ціни: фіксована/змінна, фінальна ціна при завершенні, суми з `Decimal`;
- статуси: які переходи дозволені, чи можна редагувати завершений запис;
- вихідні дні проти записів (запис на вихідний);
- аналітика: межі тижня/місяця/року, перший день тижня, часовий пояс, дохід за годину,
  середній чек, топ послуг/клієнтів, порожні періоди (ділення на нуль);
- профіль, мова, валюта, спеціалізації: відновлення після входу і після перезапуску;
- реєстрація і вхід: усі помилки показуються користувачу.

## 5. Якість коду: знайти й перелічити
- мертвий код, заглушки, `TODO`/`FIXME`, `mock`, файли, яких немає в target;
- `print(...)`, особливо з персональними даними;
- примусові `!`, `try!`, а також `try?`, що мовчки ковтають помилки збереження;
- тексти в UI без локалізації; ключі, яких бракує в одному з 5 файлів `Localizable.strings`,
  і ключі, які ніде не використовуються;
- кольори, шрифти й відступи, задані напряму (`.pink`, `Color(red:...)`, `.white`, числа), а не через `ThemeManager`;
- дублювання коду (однакові View/функції в кількох місцях);
- потенційно повільні місця (великі `@Query` без фільтра, завантаження фото в головному потоці).

## 6. Перелік функцій (`features.md`)
Таблиця: функція → як нею користується майстер (1 речення) → де в коді. Окремо позначити «розумні»
функції: захист від накладок, захист від дублікатів, найближчий вільний слот, змінна ціна,
аналітика тощо. Цей файл піде в опис продукту та в порівняння з конкурентами, тож нічого не пропускай.

## 7. Інвентар UI (`ui-inventory.md`)
Підготовка до дизайн-системи:
- усі різновиди кнопок, карток, рядків списку, полів вводу, чіпів, бейджів статусів, порожніх
  станів, алертів; для кожного: як виглядає, де використовується (файл:рядок), чи повторюється;
- усі кольори з `ThemeColors` і де вони використовуються; усі кольори, задані напряму;
- шрифти й розміри тексту; відступи й радіуси заокруглень;
- як зараз реалізовані 3 теми і що в них насправді відрізняється.

## 8. Скріншоти
Напиши UI-тест `ScreenshotTourTests`. Він реєструє тестового майстра, заповнює демо-даними
(5–8 клієнтів, послуги, записи на тиждень, кілька завершених) і проходить по КОЖНОМУ екрану:
вітання, вхід, кроки реєстрації, Головна, Клієнти, картка клієнта, нова/редагування клієнта,
Календар, новий запис, завершення запису, Послуги, Аналітика (тиждень/місяць/рік), Налаштування,
тема, мова, спеціалізація. Скріншоти зберегти в `docs/audit/screenshots/` для кожної з 3 тем.
Демо-дані тільки вигадані (без реальних людей).

## 9. Формат звіту `REPORT.md`
1. Коротко: загальний стан додатку в 5–7 реченнях.
2. Архітектура (діаграми).
3. Знахідки: таблиця «№ / Серйозність (🔴 критично, 🟠 важливо, 🟢 дрібниця) / Що не так /
   Де / Чим загрожує / Як виправити».
4. Результати тестів бізнес-правил.
5. Пропозиція: список майбутніх задач (заголовок + 2–3 речення), згрупованих за пріоритетом.
   Їх можна буде одразу перенести в GitHub Issues.

Після завершення: коміт, і коротко розкажи Сергію головне (топ-5 знахідок).
